## E2E / 测试

### [2026-10-22] doc 通知渠道强制 https，本地明文接收器无法直连验收（阶段二门禁）
- **现象**：门禁要求「报警 30s 内 POST 到本地 http 接收器」，把 `http://host.docker.internal:<port>/hook` 写入 `doc.settings.notify` 时被 422 拒绝；改走 DB 直改绕过校验又只验证到运行时半条链路。
- **根因**：渠道模型对 webhook/钉钉/企微 URL 强制 `^https://`（Task 4 防明文出口泄漏 access_token/secret 的刻意约束），验收计划假定可写明文 URL 与之冲突。另两个坑：notify 节流 `ALARM_NOTIFY_THROTTLE_SEC=300`（同规则）使「渠道生效后第二条报警」不外发——晚于首条报警启动的监听脚本会误判链路失败；报警列表 `status` 合法值是 `triggered/acked/cleared`（无 recovered）。
- **解决**：接收器侧上 TLS——server venv cryptography 自签 CA + `host.docker.internal` 叶证书，CA `docker cp` 进 server 容器后以 root 追加进 certifi bundle（notify 每次发送新建 httpx client、逐次重读 CA 文件，注入即时生效）；doc 走正常 PUT 写 `https://host.docker.internal:<port>/hook`（schema 合法，PUT 路径同被验证）；断言锚点改为「doc updatedAt（渠道生效时刻）之后触发的报警，其 alarmId 对应 POST 距 triggered_at ≤30s」。实测报警后 0.07s 到达。Docker Desktop 下容器访问 `host.docker.internal` 可直达宿主 127.0.0.1 绑定端口（无需 0.0.0.0）。验毕容器内 certifi 按备份还原。
- **预防**：外发 webhook 类验收先查渠道 URL 方案约束，本地接收器默认按「TLS 接收器 + 容器 CA 注入」准备；时序断言必须考虑 notify 节流窗（缺省 300s）与「渠道为空时不占节流」的语义（渠道生效后第一条报警必发）。

### [2026-10-20] Playwright URL 通配匹配失灵
- **现象**：`waitForURL`/`expect(page).toHaveURL` 用 `**` 通配断言不生效或超时。
- **根因**：glob 匹配规则与直觉不符（`**` 不覆盖路径段的预期组合）。
- **解决**：改用精确前缀字符串（如 `http://localhost:5199/editor/`）断言。
- **预防**：E2E 中 URL 一律用精确前缀，不用通配符。

### [2026-10-20] Element Plus 受控输入 fill 无效
- **现象**：`locator.fill()` 后组件值未变或校验不触发。
- **根因**：受控组件依赖 input 事件链，fill 的合成赋值不走完整事件流。
- **解决**：改用键盘事件注入（`pressSequentially` / `type`）。
- **预防**：对 el-input / el-select 一律键盘注入；写操作前先 blur 触发校验。

### [2026-10-21] 连续跑 E2E 后段用例卡在登录页
- **现象**：整套 13 条冒烟跑完，后段用例停在 `/login`（用户名密码已填、点「进入控制台」不跳转）；单独重跑该文件全过。
- **根因**：`/api/v1/auth/login` 按 IP 限流（`REST_LOGIN_PER_MIN` 默认 10 次/分钟），每条用例都走一次 UI 登录，超过阈值即 429；前端只在表单下方提示，用例侧表现为「登录没反应」。
- **解决**：分文件跑，或测试环境设 `RATE_LIMIT_ENABLED=false`；断言前先判 429 并显式报错。
- **预防**：E2E 登录态优先复用 Playwright `storageState`，不要在每条用例里重复 UI 登录。

### [2026-10-20] pytest-asyncio 跨测试复用引擎导致「串库」
- **现象**：测试单跑通过、全量跑时数据互相污染。
- **根因**：pytest-asyncio 每个测试一个事件循环；StaticPool 的单条连接绑定首次使用的循环，跨测试复用即错乱。
- **解决**：conftest 每测试重建引擎 + 会话工厂（`db_env` fixture），结束 drop_all + dispose。
- **预防**：新增全局连接/引擎类单例时，必须挂进 per-test 生命周期，不做模块级缓存。

### [2026-10-20] 测试环境变量设置时机错误
- **现象**：测试读到生产默认配置（如 JWT_SECRET=CHANGE_ME）或 settings 校验失败。
- **根因**：pydantic-settings 在**导入时**读取 env，conftest 里 import app 之后再 `os.environ[...]=` 已无效。
- **解决**：conftest 顶部先设 env 再 import app。
- **预防**：任何「导入即求值」的模块级配置，测试侧必须保证 env 先行。

### [2026-10-25] pytest 全量 collection 失败：No module named 'tests'
- **现象**：`cd server && .venv/Scripts/pytest` 全量跑时 5 个文件 collection 报 `ModuleNotFoundError: No module named 'tests'`（它们用 `from tests.conftest import make_doc`），单文件跑有时正常。
- **根因**：`tests/` 不是包、`pyproject.toml` 也没把 `server/` 放进 `sys.path`；能否导入取决于 pytest 的 rootdir/cwd 推导，入口不同结果不同。
- **解决**：`[tool.pytest.ini_options]` 增加 `pythonpath = ["."]`（比新增 `tests/__init__.py` 影响更小，不改变包的解析语义）。
- **预防**：测试内引用同包辅助时，显式声明 pythonpath，不依赖 pytest 的隐式路径推导。

## 前端

### [2026-10-21] 台账缩略图一直空白（截图失败 + 保存竞态双因）
- **现象**：工程台账卡片视图全部显示「保存后自动生成预览」，`projects.doc` 里根本没有 `project.thumbnail`。
- **根因 1**：`TitleBarWidget` 用了 `color-mix(in srgb, currentColor 10%, transparent)`（Chrome 111+）。html2canvas 解析不了这类颜色函数，整页截图直接抛 `unsupported color function "color"`；而 `captureThumbnail` 的 catch 是静默的，于是「保存成功、缩略图永远为空」且无任何线索。
- **根因 2**：手动保存是「先截图、后 PUT」，截图（html2canvas）耗时数百毫秒；期间 3s 防抖的自动保存先触发，把**不含缩略图**的 doc 落库并清掉 `dirty`，随后手动 `save()` 因 `!dirty` 直接返回——缩略图只写进了内存。
- **解决**：标题栏渐变改固定 `rgba()`（同时满足 Chrome 90 基线）；截图 catch 加 `console.warn`；`saveWithThumbnail` 开头清掉待触发的自动保存定时器；`setThumbnail` 标脏（dataURL 相同则跳过）。
- **预防**：html2canvas 不支持 `color-mix`/`color()`/`oklch` 等现代颜色函数，画布上任何一处出现都会让整页截图失败；异步副作用（截图/上报/统计）必须和「标脏 → 保存」的时序显式绑定；静默 catch 一律留日志。

### [2026-10-21] 大屏长时间停留：SVG 动画每秒触发数十次布局
- **现象**：分享页开着不动 2 分钟，Layout 计数从 180 涨到 7200+（≈60 次/秒），低配一体机持续发热、交互发涩；但 JS 堆稳定在 30MB 左右，不是内存泄漏。
- **根因**：`TankWidget` 用 SVG SMIL `<animate attributeName="y">` 做液面波动。SMIL 每帧改几何属性 → 整页 layout。改成 SVG 子元素的 CSS `transform` 动画后实测仍有 40+/s layout（Chrome 对 SVG 子元素变换不做合成，仍走主线程布局）。
- **解决**：液面波动改为 HTML 覆盖高光条的 `transform` 动画（合成层，零 layout）；管道流动的 `background-position` 动画改为扩展伪元素的 `translateX`（节点 `overflow:hidden` 裁剪）；顺带修掉水箱渐变/clipPath 的重复 `id` 串色问题。另：`AudioContext` 卸载即 close（浏览器上限约 6 个）、`serverAckedAlarmIds` 封顶 2000、历史落盘 10s→60s。
- **结果**：layouts 60/s → 7~14/s；180s 采样 heap 30–34MB 波动、nodes/listeners 无单调增长。
- **预防**：常驻大屏页面禁用 SMIL、SVG 子元素动画、`background-position` 动画；只保留 `transform`/`opacity`；所有长驻缓冲（历史/事件/ack id）必须封顶，并用 CDP `Performance.getMetrics` 长跑验收而非只看内存。

### [2026-10-21] 属性面板输入后 Delete 删不掉组件
- **现象**：在右侧属性面板编辑过任意输入框后，点画布选中组件按 Delete 无反应；先点一下空白或切页后恢复。
- **根因**：`CanvasNode` 的 pointerdown 调了 `preventDefault()`（防文本选择/原生拖拽），这会连带阻止浏览器把焦点从输入框移走；焦点仍在 `el-input` 里，键盘层 `isTypingTarget` 判定为「输入中」直接吞掉 Delete。组内删除后 `selection` 未清空也会留下幽灵 id，让下一次 Delete 空转。
- **解决**：画布（节点/缩放柄/旋转柄/空白）pointerdown 先 `blurTypingTarget()`；`deleteSelection` 先把选中收敛到当前上下文真实存在的 id 并清空；预览/数据抽屉打开时画布快捷键整体旁路（`installKeyboard(store, isBlocked)`）。
- **预防**：凡是 `preventDefault()` 接管点击的画布/拖拽区，都要显式处理焦点转移；快捷键层对「输入中」的判定依赖焦点，不能只依赖事件 target。

### [2026-10-21] 编辑器拖动/编辑「不丝滑」的四个来源
- **现象**：大画幅页面拖动组件偶发掉帧；连续编辑时每隔几秒卡一下；缩放坞附近移动有明显重绘。
- **根因**：① `pointermove` 逐事件写 doc + 重算吸附，高刷鼠标一帧内处理多次；② 每个 move 里 `getBoundingClientRect()` 触发同步布局；③ 自动保存（3s 防抖）每次都跑 `html2canvas` 整页截图，主线程被占数百毫秒；④ 缩放坞 `backdrop-filter: blur(6px)` 在画布重绘时每帧重算模糊。
- **解决**：move 用 rAF 合帧（抬起前强制 flush 末帧）；手势开始缓存视口 rect；缩略图截取节流 30s，手动保存/导出/分享/离开才 force；去掉 backdrop-filter；`setNodeRect` 同值不写；舞台加 `will-change: transform`。
- **预防**：交互热路径禁止逐事件做布局读取与全量序列化；任何「保存后副作用」（截图/上传/统计）都要节流或移出主线程。

### [2026-10-21] 文本组件多行文案被压成一行
- **现象**：画面模板里的图例/说明（`\n` 换行）渲染成一长条，只能看到第一行。
- **根因**：`TextWidget` 的 `ellipsis` 默认 true（`white-space: nowrap`），而 demo/模板工厂的 `txt()` 不传该字段。
- **解决**：多行文案改走显式 `props.ellipsis = false` 的工厂（pageTemplates 的 `lines()`）。
- **预防**：用 `\n` 排版前先确认组件是否 nowrap；模板类工厂对「多行文本」单独封装，不靠默认值。

### [2026-10-21] 深色画布上模板文字/数值「消失」
- **现象**：新套用的画面模板里状态文本、变量读数、开关标签看不见（深底黑字）。
- **根因**：`text` / `var-display` / `state-text` / `switch` 等组件文字色缺省 `inherit`，画布底色深而根节点没有设 `color`，最终继承到黑色。
- **解决**：模板内所有文字类组件显式给 `style.color`；状态文本用 states 的 `color/background` 做药丸底色。
- **预防**：深色画布的静态模板不得依赖继承色；新增模板/演示页截图验收时检查「最低对比度」。

### [2026-10-21] `:has()` 与 Chrome 90 基线冲突
- **现象**：图层面板想用 `:has(.back-btn)` 给「组内编辑」态换强调色，写法简洁但会静默失效。
- **根因**：`:has()` 需要 Chrome 105+，项目基线是 Chrome/Edge ≥ 90（build target es2020）。
- **解决**：改为模板上绑条件 class（如 `:class="{ 'in-group': ... }"`）。
- **预防**：CSS 新特性先对照基线再写；`:has()`、容器查询在基线内不可用，条件样式一律走模板 class。

### [2026-10-20] vite 代理不转发 WebSocket，运行态永挂「连接中」
- **现象**：大屏运行态 WS 一直连不上，接口轮询正常。
- **根因**：vite 代理写成简写字符串形式不转发 Upgrade 升级请求。
- **解决**：`proxy: { '/api': { target: ..., ws: true } }`（web/vite.config.ts）。
- **预防**：项目内凡是 `/api` 代理配置必带 `ws: true`。

### [2026-10-20] dev 端口被占静默漂移，E2E 打错地址
- **现象**：本机 5173 被其他应用占用，vite 静默换端口，E2E 仍打 5173 指向无关应用。
- **解决**：`server.port: 5199, strictPort: true`——被占直接报错。
- **预防**：E2E 依赖的 dev server 一律 strictPort；改端口需同步 E2E 脚本 BASE。

### [2026-10-20] 换账号后旧角色缓存污染新会话
- **现象**：admin 退出换 viewer 登录，仍能进 /admin 管理页。
- **根因**：角色缓存在模块级变量；换账号后沿用旧值；且在途 `/auth/me` promise 完成后把旧角色写回缓存。
- **解决**：进 `/login` 即作废缓存与在途请求；作废用「请求身份比对」而非无脑置空，防误清并发新请求（router/index.ts `fetchMyRole`）。
- **预防**：模块级缓存凡是「会话相关」，必须提供随登出/换账号作废的入口，并处理 in-flight 竞态。

### [2026-10-25] 变量/数据源表单「整对象替换」静默清空隐藏字段
- **现象**：CSV 导入的 Modbus 变量（`modbusDataType=uint32`、`modbusByteOrder=CDAB`、`unitId=2`）在面板里只改一次名称并保存后，三个字段全部丢失，寄存器按 int16+ABCD 解码，历史曲线与报警阈值集体错值且没有任何报错；同理，编辑一个正在采集的 Modbus 数据源并保存，`buildConfig()` 无 `modbus` 分支返回 `{}`，host/port/unitId 被清空，在产采集当场断。
- **根因**：`saveVar` 构造新对象时只列了表单覆盖的字段，再用 `doc.variables[idx] = item` 整对象替换；`saveDs` 同样用 `buildConfig()` 的返回值整体替换 config。表单之外的字段（bitIndex / modbus* / unitId / range / description；timeoutMs / staleTimeoutMs / reconnect*）没有「保留」语义。
- **解决**：两处都改「先展开旧对象、再覆盖表单字段」：`saveVar` 用 `{ ...existing, ...表单字段 }`，并在目标数据源非 modbus 时显式把三个 Modbus 字段置 null；`saveDs` 在同类型编辑时 `{ ...prev.config, ...buildConfig() }`，换类型才整份替换。同时补 `buildConfig` 的 modbus/opcua 分支与 OPC UA 表单、类型下拉。
- **预防**：凡是「表单只覆盖部分字段」的编辑，必须用合并写入而不是整对象替换；新增字段时先问「哪个编辑入口会把它弄丢」。用「导出→改一项→重导→再导出」的往返用例钉死字段守恒。

### [2026-10-25] 点位 CSV 只能新增不能更新，改版点表只能删掉重导
- **现象**：业主把点表里的地址改了几十个，重新导入时同 key 全部被跳过；要更新只能逐条删变量再导，绑定跟着断。
- **根因**：导入实现是「push 新变量 + 已存在 key 跳过」，没有 upsert 语义；变量表也没有导出入口，产品只是 Excel 的可视化外围。
- **解决**：变量表加 CSV 导出（与导入同格式、可往返）；导入改为按 key upsert（CSV 省略的列保留旧值，虚拟变量 key 冲突跳过并提示）；**已有变量保持各自原数据源**（所选目标源只用于新增变量，否则一次全表导入会把所有变量搬到同一个源并清掉 Modbus 字段）；预览区分新增/更新/冲突；删除变量/数据源前扫描绑定/事件/props/报警规则并阻断。
- **预防**：批量导入默认按业务主键 upsert，不要默认「重复即跳过」；跨对象批量更新必须区分「更新内容」和「不改身份字段」；破坏性操作前必须能回答「影响谁」。

## 后端

### [2026-10-22] 报警状态机/判定引擎测试随机挂 InvalidRequestError（notify 并发读库扰动）
- **现象**：通知渠道落工程 doc（send_alarm 改为派生任务并发读 doc 解析渠道）合入后，`test_alarm_state_machine` / `test_rules_engine` 每次挂的用例都不同，报 `InvalidRequestError: Could not refresh instance`，单跑即过、干净树 3 连过。
- **根因**：双因叠加。① 这两个文件用 StaticPool 单连接引擎，多会话共享同一条连接，`trigger()` 的 `commit→refresh` 窗口可被并发会话的 BEGIN/ROLLBACK 干掉未提交 INSERT（测试基建固有脆弱面，生产 PG 独立连接无此问题）；② 未注入 `notify.session_factory` 时落到模块级 SessionLocal（import 期创建的 :memory: StaticPool 连接），跨 pytest 每测试新事件循环使用本身就未定义，异步扰动把①的碰撞概率从近零放大到 ~30%。
- **解决**：两个文件加 autouse `_stub_notify` fixture 打桩 `notify.send_alarm`（沿既有 `fake_ws`/`audit_seam` 打桩惯例；外发链路自有 test_notify.py 覆盖），10 连跑全绿。
- **预防**：新服务若在报警/采集派生任务里并发开 DB 会话，必须提供 session_factory 测试缝；不测该链路的文件一律打桩，别让模块级 SessionLocal 引擎跨事件循环被碰。

### [2026-10-22] JSON 列就地改值后 `p.doc = dict(p.doc)` 不落库
- **现象**：测试里改 `project.doc` 嵌套字段后整体重赋值 `dict(p.doc)`，commit 成功但库内旧值（UPDATE 语句根本没发）。
- **根因**：SQLAlchemy flush 按新旧值 `==` 判定净变更，`dict(p.doc) == p.doc` 为真 → 不标脏不发 UPDATE（应用侧写 doc 一律走 Core `update().values()`，无此坑；只有测试拿 ORM 实例直改才踩）。
- **解决**：测试用 `sqlalchemy.orm.attributes.flag_modified(project, "doc")` 显式标脏。
- **预防**：测试直改 JSON/JSONB 列时用 flag_modified（或改走 Core update），不要依赖重赋值触发脏标记。

### [2026-10-22] 本地 SQLite 跑 alembic upgrade head 在 0002 处 NotImplementedError
- **现象**：新写迁移 0003 后想本地冒烟，`alembic upgrade head` 直接抛 `NotImplementedError: No support for ALTER of constraints in SQLite dialect`。
- **根因**：0002 迁移用了 `op.create_check_constraint` / `op.drop_constraint`，SQLite 方言没有 ALTER 约束能力（alembic 需 batch 模式）；迁移链本来就只面向 PG，CI 的 alembic 冒烟在 PG16 service 上跑。另：Git Bash 下 `$(pwd)` 拼进 `sqlite+aiosqlite:///` URL 会得到打不开的混合路径。
- **解决**：本地验证单个迁移用「空库 `alembic stamp <prev>` + `alembic upgrade head`」，只跑新增段；SQLite URL 用 `sqlite+aiosqlite:///C:/绝对路径.db` 形式。
- **预防**：新增迁移写完，本地冒烟走 stamp 法验证新段可执行，全链验证交给 CI 的 PG16；测试侧表结构由 conftest `create_all` 覆盖，不依赖迁移。

### [2026-10-20] uvicorn 访问日志泄漏 WS token
- **现象**：安全审查发现 `/api/v1/ws/runtime?token=...` 完整进日志。
- **根因**：token 走查询串（浏览器 WS 无法带 Header），uvicorn access log 原样记录。
- **解决**：uvicorn `--no-access-log`，访问日志统一由 nginx 层输出（对 token 掩码）。
- **预防**：新增任何查询串传敏感值的端点，必须检查两层日志路径。

### [2026-10-25] 虚拟变量拿坏值/停更旧值继续计算，输出「正常值」
- **现象**：PLC 断线后单点质量位已变 bad/stale，界面也显示灰色，但由它派生的虚拟变量仍保持 GOOD，继续按最后一帧旧值算出正常数；基于该虚拟变量的报警与历史全部失真。
- **根因**：`hub._eval_virtual` 的 scope 取「池内所有非 None 值」，不区分质量位；`_propagate` 求值失败时直接 `continue`，既不更新池也不广播，虚拟变量停在上一轮 GOOD；`sweep_stale` 只翻单点质量位，不向下游传播。
- **解决**：scope 只收 `q == good` 的值；求值失败时把虚拟变量以 bad 写回池并广播（已是 bad 则不重复广播）；`sweep_stale` 收集翻转 key 后逐个 `_propagate`。新增用例 `test_virtual_variable_turns_bad_when_dependency_stale`。
- **预防**：任何派生计算都必须把「输入质量」当一等输入；「求值失败」不能静默保留旧结果，要么转 bad，要么明确标注为保持值。质量位只在 UI 显示而不驱动计算，等于没有质量位。

### [2026-10-25] 坏值传导的边界：常量型/计算型变量不能按时间判 stale
- **现象**：把「依赖坏值 → 虚拟变量转 bad」落地后，演示工程的 hold 型 mock 变量（只推一次初值）5 秒后被 sweep_stale 翻成 stale，依赖它的虚拟变量（加载台数等）从此恒为 bad；同理，OPC UA 订阅在值不变时不再推帧，稳态点位也会被误判 stale。
- **根因**：stale 的本意是「该来帧却没来」，但 hold 常量、计算点、订阅型稳态点的「没有新帧」不等于「数据失效」。
- **解决**：`_effective_stale_ms` 对虚拟变量与 `mock.kind='hold'` 返回 0（不参与超时）；OPC UA 健康探测每 1s 调 `hub.touch()` 推进订阅变量的新鲜度（只推进 good 条目）。坏值传导仍保留：只有真正 bad/stale 的输入才会让下游转 bad。
- **预防**：设计质量位传播前先给变量分类（流式/常量/计算/订阅），「新鲜度」判定必须按类定义；否则一次正确的传导规则会在另一类变量上制造大面积误报。

### [2026-10-25] historian 同窗口按到达顺序覆盖，乱序帧让历史时间轴倒退
- **现象**：网关重发/网络乱序时，同一 5s 窗口内较旧的样本后到，覆盖掉较新的样本，历史曲线出现时间倒退点。
- **根因**：`_pending[(pid,key)]` 直接赋值，注释与实现都是 last-write-wins（按到达顺序），没有比较样本时间戳。
- **解决**：入缓冲前比较 `ts`，旧于已缓冲样本的帧直接丢弃；新增 `test_window_out_of_order_keeps_newest`。
- **预防**：所有「按 key 去重」的时序缓冲，必须明确按事件时间还是到达时间取胜；工业数据默认按事件时间最大。

### [2026-10-25] 载荷时间戳不校验：未对时/retained 旧消息污染历史与报警统计
- **现象**：上游 PLC 时钟未对时，或 MQTT retained 消息带旧时间戳时，历史里出现几小时前甚至去年的点，按时间聚合的班报/报警统计被系统性拉偏。
- **根因**：`_frame_ts` 解析出时间戳就直接使用，未与本地时钟比对；接口契约（03 §2.7）要求偏差 >±300s 回落当前时间并告警，代码未实现。
- **解决**：`FRAME_TS_MAX_SKEW_MS`（默认 300000）可配；超限回落 `now` 并按 tsPath 只告警一次。新增 `tests/test_collector_ts.py` 覆盖毫秒/秒/ISO/超限/非法五类输入。
- **预防**：外部时间戳一律当不可信输入；先做偏差门限再入库，同类告警做去重，避免刷爆日志。

### [2026-10-25] 通讯中断不能只靠变量 stale 判断
- **现象**：想用「变量 q=stale」推导设备离线，但 OPC UA 订阅只在值变化时推送；稳态点位永远不更新帧，会在连接完全正常时被判 stale；反之 MQTT 连接已死但值未变，也可能迟迟不报。
- **根因**：把「数据新鲜度」与「链路存活」混为一谈。不同源推进新鲜度的机制不同（轮询每周期、订阅看变化、长连接靠心跳）。
- **解决**：采集源维护独立的 `state/last_ok_ms`（连接成功/收发/心跳/健康探测推进），`comm_monitor` 5s 扫一轮，静默超阈值触发 `sys_comm:<dsId>` critical 报警，恢复自动 clear；阈值按源类型区分（轮询 3×周期、OPC UA 30s、MQTT/WS 90s）。内存断线集合必须在**写库成功之后**更新（trigger 失败要下轮重试，不能静默丢整段报警）；源下变量被删空也要走清除分支，否则报警永久悬挂；源在快照中短暂缺席（sync 的 stop await 窗）要连续 2 轮才判删除。
- **预防**：链路健康必须由链路自己证明，不能由业务数据反推；长连接要有独立心跳推进存活时间；「内存状态 + 数据库状态」双写时，先写库再改内存。

### [2026-10-25] 通知失败即丢 + 恢复不外发：值班员只知道「坏了」不知道「好了」
- **现象**：网络抖动 10s 时，critical 报警的 Webhook 三次退避后直接丢弃；设备恢复后没有任何外发，值班员只能自己盯屏确认。
- **根因**：发送是「一次调用内重试 3 次」的短事务，没有持久化；clear 路径只广播 WS，从未调用通知。
- **解决**：失败渠道落 `notification_outbox`（渠道/载荷快照，URL/secret 加密入库），后台每 3s 补发，30s 起指数退避、8 次转死信、崩溃遗留 sending 5 分钟后回收；单行解密/发送异常只影响该行（否则整轮中断、行卡 sending）；sent 保留 7 天、dead 保留 30 天由每日维护清理；`alarm_service.clear` 增加恢复通知（不受触发节流限制）。
- **预防**：跨网络的副作用一律「先持久化再发送」；状态机的两个方向（触发/恢复）必须成对设计通知；后台队列的逐行处理必须自己兜异常，不能依赖外层 try。

### [2026-10-25] 工程克隆：深拷贝 doc 后必须重写 project.id 并重新走校验
- **现象**：直接复制 doc 建新工程，编辑器打开后保存报 `project_id_mismatch`；不重写 id 也会让两个工程指向同一 project.id。
- **根因**：doc.project.id 与库内 Project.id 有强一致校验，克隆是「新身份 + 旧内容」。
- **解决**：`clone_project` 深拷贝 → 重写 id/name/author/createdAt/updatedAt、清缩略图 → 走 schema/体积/结构/引用校验与凭证加密 → revision=1 新建；凭证密文原样复制（同一 DATASOURCE_SECRET 可解）。
- **预防**：任何「复制实体」的操作都要先列出该实体里哪些字段是身份、哪些是内容；身份字段必须重新生成并重跑不变量校验。

## 部署 / 构建

### [2026-10-21] 图片上传目录在非 root 容器里不可写
- **现象**：上传接口在本地裸跑正常，进容器后写盘报 Permission denied。
- **根因**：server 镜像 `USER appuser(1000)` + compose `cap_drop: ALL`；命名卷首次挂载按镜像内目录的属主初始化，镜像里没有预建目录就会由 root 持有。
- **解决**：Dockerfile `mkdir -p /app/uploads && chown appuser:appuser /app/uploads`，compose 挂 `uploads_data:/app/uploads` 并设 `UPLOAD_DIR`；nginx `client_max_body_size 10m` 已覆盖 5MB 上限。
- **预防**：凡需落盘的容器服务，目录必须在镜像内预建并 chown，再挂命名卷；不要指望运行时 `mkdir` 能绕过属主问题。

### [2026-10-20] Dockerfile 依赖层把项目源码打进去且被旧缓存掩盖
- **现象**：依赖层构建结果异常但反复构建「看起来正常」。
- **根因**：`pip install .` 在仅含 pyproject.toml 的构建目录里打 wheel，wheel 依赖源码文件——缺失部分靠旧缓存层掩盖，问题被隐藏。
- **解决**：builder 层只装第三方依赖（venv 独立目录），运行层 `COPY app ./app` 带源码（server/Dockerfile）。
- **预防**：多阶段构建的依赖层禁止 `pip install .`；构建产物异常时先 `docker history`/`--no-cache` 排除缓存层假象。

### [2026-10-20] 镜像拉取慢 / 失败
- **解决**：基础镜像前缀走 `REG_PREFIX` build-arg（.env 可设 `m.daocloud.io/docker.io/` 等），pip/npm 用国内源。
- **预防**：新增 Dockerfile 沿用 `ARG REG_PREFIX` + 国内源惯例，不写死官方源为唯一路径。

### [2026-10-22] pymodbus「>=3.9」实装 3.16：legacy datastore 运行时写入失效
- **现象**：按 3.9 时代写法（`ModbusServerContext` + `ModbusSequentialDataBlock` + `context[0].setValues`）写仿真从站，启动即弃用告警，且运行时改寄存器不生效（`ModbusServerContext.async_setValues` 对 legacy 上下文恒返回 `DEVICE_BUSY`）。
- **根因**：pyproject 只约束 `pymodbus>=3.9`，镜像构建解析到最新 3.16.x；3.16 起 datastore 旧类弃用、底层改走 SimDevice/SimData，旧类的运行时写路径已断。
- **解决**：`scripts/sim/modbus_slave.py` 改用 `SimDevice(simdata=(co,di,hr,ir) 四区块)` + `ModbusTcpServer(...).serve_forever()`（即 `StartAsyncTcpServer` 底层，便于同进程跑后台协程），后台更新走 `server.async_setValues(unit_id, func_code, addr, words)`（fc16=HR、fc15=线圈）。
- **预防**：面向「实装版本」而非「约束下界」写脚本；用 pymodbus 新 API 前先 `inspect.signature` 对 venv 实物核对。

### [2026-10-22] asyncua 2.1.0 实装 API 与旧文档五处偏差（OPC UA 第六源）
- **现象**：按 asyncua 0.9/1.x 时代示例写 OPC UA 代码（`await server.shutdown()`、`str(nodeid)` 当地址串、`add_variable(idx, "temp", ...)` 期望得到字符串 nodeId、订阅回调直接拿 `data` 当 DataValue 用），分别报 `AttributeError: 'Server' object has no attribute 'shutdown'`、订阅静默收不到值（nodeId 匹配不上）、browse 拿到数字 nodeId 对不上变量 address。
- **根因**：pyproject 锚定 `asyncua>=2.0`，pip 解析到 2.1.0；2.x 对 Server/Client/订阅回调做了一轮不兼容重构，旧文档/示例仍在流传。
- **解决**（实装 2.1.0 正确口径，采集源在 `collector.py` OpcUaSource、测试在 `tests/test_opcua.py`）：①停服务用 `await srv.stop()`（无 `shutdown`）；②NodeId ↔ 字符串互转必须 `to_string()` / `NodeId.from_string()`——`str(NodeId)` 是 Python repr（形如 `NodeId(Identifier='demo.temp', ...)`）；③显式字符串 nodeId（`ns=2;s=demo.temp`）须 `add_variable(f"ns={idx};s=demo.temp", f"{idx}:temp", v)` 两参显式形式，`add_variable(int首参, 名字)` 生成的是数字 nodeId；④订阅回调签名 `datachange_notification(node, val, data)` 的 `data` 是 `DataChangeNotif`，时间戳/质量位在 `data.monitored_item.Value.{SourceTimestamp,StatusCode}`；⑤Server 动态端口写 `:0`，启动后从 `srv.bserver.port` 取实际端口（测试随机端口 fixture 用它）。另：断线不向用户代码抛错（后台 publish 循环自吞），需 `client.check_connection()` 轮询探测（本源 1s 周期）。
- **预防**：同 pymodbus 条目——面向实装版本写代码，新版依赖先跑最小 spike（Server 起停/订阅/browse/断线重启四象限）核对 API 形状再写正式实现。

### [2026-10-22] compose 复用 server 镜像跑旁路脚本：command 覆盖不生效
- **现象**：给 sim 服务只写 `command: python /app/sim/xxx.py`，容器仍走「等 DB → alembic → uvicorn」启动序然后退出/卡住。
- **根因**：server 镜像 `ENTRYPOINT ["bash","entrypoint.sh"]` 写死启动序且不 `exec "$@"`，compose `command` 只是 entrypoint 的参数。
- **解决**：sim 两服务显式 `entrypoint: []`（或 `entrypoint: ["python"]`）再给 command，绕开 uvicorn 入口。
- **预防**：凡复用应用镜像跑一次性/旁路容器（tls-init 已是先例），必须先看镜像 ENTRYPOINT 是否 `exec "$@"`，否则一并覆写 entrypoint。

### [2026-10-22] compose up 不重建已存在镜像：代码更新后验收打在旧容器上
- **现象**：阶段一端到端首跑，WS 收到 m_temp=16828（即 0x41BC 被按 int16 读）、通配变量 any_run 恒无值——全是旧版逐变量读/全等匹配的行为；而 sim 两容器行为正常。
- **根因**：`docker compose up -d` 对已有 tag 只复用不重建；且 sim 两服务镜像名独立（webscada-sim-modbus / webscada-sim-mqtt-gateway），构建 sim 完全不刷新 webscada-server——栈里 server 容器仍是 8 小时前旧镜像建的。
- **解决**：`docker compose build server && docker compose up -d --no-deps server`；镜像内验证 `docker compose exec server grep -c plan_modbus_reads /app/app/services/collector.py`。
- **预防**：代码更新后的端到端验收，先 grep 运行容器内的新符号确认版本；共用 build context 的多服务，记住镜像名按服务名各自分账。

### [2026-10-25] 备份漏命名卷 / 恢复脚本误报失败 / 容器日志无上限
- **现象**：按 `backup.sh` 恢复后，工程里的图片全部 404、EMQX 里建的 MQTT 账号消失；本机 `.env` 设 `HTTP_PORT=8088` 时，`restore.sh` 恢复成功却报「健康检查未通过」；长期运行后宿主机磁盘被容器 json-file 日志写满。
- **根因**：备份只做了 `pg_dump` + doc JSONL，`uploads_data`、`emqx_data` 不在数据库里；`restore.sh` 用 `${HTTP_PORT:-80}`，而 `.env` 只被 docker compose 消费、不会进入当前 shell；compose 各服务没有 `logging` 配置，json-file 默认无大小上限。
- **解决**：backup 增加 uploads/emqx 的 tar.gz（失败只告警不中断）并纳入保留期清理；restore 用 `docker compose port nginx 80` 取实际映射端口；compose 增加 `x-logging` 锚点（20m × 5）挂到 postgres/emqx/server/nginx。
- **预防**：备份清单按「数据存在哪」列全，而不是按「数据库里有什么」；脚本读配置一律以运行时实际值为准（compose port / inspect），不要假设 shell 有 `.env`；任何长期驻留容器必须显式设日志轮转。

### [2026-10-25] 离线交付包会把构建机私钥与密钥固化进去
- **现象**：`cp -r deploy` 打包时把 `deploy/certs`（含自签私钥）一起带走；`docker compose config` 默认会把 `${JWT_SECRET}` 等变量展开成构建机 `.env` 的明文写进交付包。
- **根因**：交付包按「目录全量复制」而不是「运行期必需清单」收集；compose config 默认插值。
- **解决**：打包时删除并重建空的 `deploy/certs`（目标机首启由 tls-init 自签）；`docker compose config --no-interpolate` 保留 `${VAR}` 占位，由目标机 `.env` 展开；`install.sh` 现场生成随机 JWT/数据库/管理员口令；备份脚本排除证书目录。另把构建时的 `REG_PREFIX` 写入 `package.env`，安装/升级同步进 `.env`——否则 `images.tar` 里是镜像站前缀名，目标机却按 `docker.io/...` 去找，离线机直接 image not found。
- **预防**：交付包用白名单收集，不用整目录复制；凡「配置即密钥/镜像名」的构建期变量，都要随包携带并在目标机落地；凡 `set -e` 的升级脚本，「启动」步骤失败必须显式转回滚。

### [2026-10-22] 门禁结果引用了旧状态：提交态模板破损但申报 vue-tsc 零错误
- **现象**：DataDrawer 插入「通知」tab 的编辑落位错误（通知 tab-pane 嵌进报警表「级别」列后、「操作」列前，三层标签未闭合、报警操作列丢失），提交后审查方用 @vue/compiler-sfc 实测 parse/compileTemplate 各报 1 个 "Element is missing end tag"；而实现者申报「vue-tsc 零错误」——那次 vue-tsc 跑在早于后续文件状态变化的时点，结果被沿用到了提交。
- **根因**：中途做过 `git stash`/`pop` 循环（排查测试波动用），工作树内容经外部工具往返后与编辑器上下文认知脱节；此后未在最终（提交）态重跑 vue-tsc/vite build，把早期门禁输出当成提交态结果写进了报告。
- **解决**：修复模板结构（报警 tab 补回「操作」列与三层闭合、通知 tab 移到其后）；门禁在提交态重跑：vue-tsc 0 错误、vite build 成功、@vue/compiler-sfc parse/compile 双检 0 错误。
- **预防**：任何外部往返（stash/checkout/其他工具改盘）之后，编辑前必须重读文件、提交前必须在当前工作树重跑全部门禁；报告只引用「最后一次文件变更之后」的命令输出，跨轮次的旧输出一律作废。
