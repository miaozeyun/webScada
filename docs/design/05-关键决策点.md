## D1 画布拖拽引擎

**背景**：P0 要求自由坐标布局（可重叠、任意 x/y/w/h）、8 向缩放、旋转、对齐吸附、成组整体位移。用户点名评估 vue-grid-layout 与 re-resizable。该决策是前端工作量最大、与撤销重做耦合最深的单点。

**选项**：
- A 完全自研：pointer events（pointerdown/move/up + setPointerCapture）+ 组件 x/y/w/h 状态 + CSS transform 定位旋转 + 自研吸附参考线。
- B 网格布局库：vue-grid-layout 官方版本（jbaysolutions）面向 Vue 2，Vue 3 需使用其同源移植 grid-layout-plus。
- C re-resizable + 自研拖拽混合。

**利弊对照**：

| 选项 | 优势 | 代价与风险 |
|---|---|---|
| A | 坐标模型与需求同构；吸附参考线、框选、成组、undo 提交点全部自定义，与 D7 快照栈天然一致；零第三方依赖 | 需自研吸附参考线与 8 向 resize 柄，估计 500~800 行；旋转后命中检测等边界情况需自理 |
| B | 拖拽/缩放/占位碰撞开箱即用 | 如实评估：其模型是 cols/rows 栅格排版，拖拽结果吸附栅格单元、碰撞时把其他组件“挤开”，与组态画面“组件可重叠、位置任意”语义直接冲突；不支持原生 rotate（外层再包 transform 会使命中测试错位）；像素级定位需极小栅格粒度模拟，占位与取整逻辑仍在，等于绕开其核心能力只用其 pointer 处理。后期发现不合适迁回 A，M1 返工 |
| C | —— | 如实评估：re-resizable 是 React 组件库，无 Vue 版本，在 Vue3 工程中不可用，该混合方案不成立；等价物退化为 A（8 向 resize 柄自研成本很低）或引入用户未点名的 Vue resize 库，不建议 |

**对架构的影响**：决定 `web/editor/canvas/*` 是否存在及 M1 工作量结构；undo 提交点定在 pointerup。
**耦合关系**：选 A → D7 配套选 A（松手入快照栈）；若选 B → undo 须按栅格坐标 diff，且旋转/重叠能力受限需向用户书面声明降级。
**落地：正文已按建议值 A（完全自研）落地（自由坐标 + 8 向 resize + 自研吸附参考线，undo 提交点=pointerup）；若改选 B（栅格布局库），需改动 `web/editor/canvas/*` 与 M1 工期结构，D7 撤销重做须改按栅格坐标 diff，且旋转/重叠能力受限需书面声明降级；若改选 C，等价退化为 A（见利弊表）。**

## D2 MQTT 数据通路

**背景**：设备经 EMQX 上报，浏览器要看到值。固定栈要求浏览器端实时通信用**原生 WebSocket**。

**选项**：
- A 后端桥接：FastAPI 用 aiomqtt（基于 paho-mqtt 的 asyncio 封装）订阅 EMQX → hub → ws_manager 广播。
- B 浏览器直连：mqtt.js over WebSocket 连 EMQX 的 WebSocket 监听（默认 8083），前端直接收原始主题。
- C 混合：主链路 A，仅开发调试构建按环境变量门控允许浏览器直连。

**利弊对照**：

| 选项 | 优势 | 代价与风险 |
|---|---|---|
| A | 浏览器只依赖原生 WebSocket（严格符合固定栈）；MQTT/REST/WS/Mock 四源同进程汇合，hub 一条总线；告警在服务端统一评估并落库；后端 1 条连接对 EMQX，浏览器连接数与设备解耦；broker 凭证只在服务端（配合 D10 脱敏） | 后端是数据必经点，单 worker 单点（`restart: always` 兜底，骨架 R6 已声明）；aiomqtt 断线重连需自行实现指数退避 |
| B | 少一跳；后端宕机时画面仍收值 | 必须引入 mqtt.js 浏览器库，违背“浏览器端原生 WebSocket”的固定栈；告警仍需后端评估落库 → 数据双路，前端自行合并、口径易分裂；每个浏览器一条 MQTT 连接，EMQX 连接数随客户端放大；分享页匿名用户也要持有 broker 凭证或逐人建 EMQX 账号，部署复杂度转嫁给中小工厂；无统一 snapshot，多端首帧一致性靠各自订阅时序 |
| C | 调试期可直看原始主题 | 多一条依赖与门控逻辑；调试收益可用“变量测试注入面板”（附录 A 第 11 条）替代 |

**对架构的影响**：决定 collector 是否为唯一数据入口；决定告警引擎落点（D3）；决定凭证暴露面（D10）。
**耦合关系**：若 D2=B，则 D3 无法独立选 A（数据双路），D10 凭证暴露面需重评，realtime 的 snapshot 一致性机制失效需重设计。
**落地：正文已按建议值 A（后端桥接：aiomqtt 订阅 EMQX → hub → ws_manager）落地；若改选 B（浏览器直连），需改动 realtime（数据双路与 snapshot 一致性重设计）、collector 唯一入口定位，并联动重评 D3/D10（见第 2 节）；若改选 C，需改动构建门控与环境变量配置（调试收益可用附录 A 第 11 条测试注入替代）。**

## D3 告警判定位置

**背景**：阈值规则需要“触发 → 落库 → 推送 → 恢复”闭环。判定侧决定记录语义、多端一致性与实现份数。

**选项**：
- A 后端引擎：rules_engine 进程内随工程保存热更新，触发/恢复写 `alarm_records`，经 WS 即时帧广播。
- B 前端判定：每个运行页自行评估规则。
- C 混合：后端判定为准，前端在 WS 断线窗口用最后值 + 本地规则做临时提示。

**利弊对照**：

| 选项 | 优势 | 代价与风险 |
|---|---|---|
| A | 报警记录全局唯一、多端一致；页面未打开也产生记录（值班语义）；规则只实现一份，回差/持续时长/恢复状态机可用 pytest 单测 | 规则热更新需监听工程保存事件（已设计）；与 D8 强耦合——若换算留在前端（D8A），后端只能按原始值判阈值，出现“显示 72.5℃、按 725 判警”的口径分裂（评审定性为不可接受） |
| B | 无后端参与，实现直观 | N 个浏览器 = N 份评估；`alarm_records` 无法可靠落库；分享页/编辑器/运行页三处同步实现；页面未打开的变量完全不产生报警；多端触发时序不一致，P0 验收项“多端同步报警”无法达成 |
| C | 断线窗口用户仍能感知异常 | 前端必须复刻回差/持续时长状态机并保持与后端行为一致，P0 收益低；断线感知可先用变量 `q=stale` 灰显表达（骨架 realtime 已含质量位） |

**对架构的影响**：决定 rules_engine 与 alarm_service 是否存在于后端；决定报警帧协议即时（不走 100ms 合帧，经 WS `alarm`/`alarmClear` 帧广播，snapshot 内嵌 `activeAlarms`）。
**耦合关系**：D8=B 是 D3A 阈值口径一致的前提；D4 选 B（Redis）时报警事件广播也须改走 Redis 通道。
**落地：正文已按建议值 A（后端引擎：触发/恢复写 `alarm_records`、WS `alarm`/`alarmClear` 帧即时广播）落地；若改选 B（前端判定），需改动 rules_engine/alarm_service 落点、`alarm_records` 落库链路与三处前端同步实现，且“多端同步报警”验收项无法达成；若改选 C，前端需复刻回差/持续时长状态机并保持与后端行为一致（P0 收益低）。**

## D4 变量运行时分发（进程内 vs Redis）

**背景**：hub 把变量值 fan-out 给 rules_engine 与 ws_manager。P0 单 worker；企业版若多实例需要跨进程分发。

**选项**：
- A 进程内 asyncio + 接口抽象：hub 定义 `publish / subscribe` 接口，当前实现为进程内队列。
- B 直接引入 Redis pub/sub。
- C PostgreSQL LISTEN/NOTIFY：复用已部署的 PG 做跨进程通知（asyncpg 原生支持监听）。

**利弊对照**：

| 选项 | 优势 | 代价与风险 |
|---|---|---|
| A | 部署组件最少（4 容器）、时延最低、无网络序列化开销；符合“能简则简” | 单 worker 硬约束（写入部署文档）；多实例时需换实现（接口已抽象，改动集中 hub.py 单文件） |
| B | 多 worker/多实例就绪，hub 无状态化 | 多一个运维组件与故障点；Redis pub/sub 为 fire-and-forget，订阅者断线期间消息丢失，仍需 snapshot 补偿——该特性在本场景没有不可替代价值；P0 规模（≤5000 变量、500ms~1s 级）远用不到 |
| C | 不新增组件 | 如实评估：NOTIFY 面向低频事件（payload 上限约 8000 字节、无持久化、同事务同 payload 会去重）；本场景峰值每秒数千条值帧会造成通知队列堆积，不适合值流；它适合的是低频控制事件（报警、工程热更新通知） |

**对架构的影响**：决定部署形态与单点声明方式；决定多实例演进路径。
**耦合关系**：D4 与 D2 同进程（A+A 时采集器与 hub 零跨进程）；若 D4=B，附录 A 第 4/5 条的重启恢复语义需重写。
**落地：正文已按建议值 A（进程内 asyncio + publish/subscribe 接口抽象）落地，配套“单 worker”硬约束写入部署文档；若改选 B（Redis pub/sub），需改动 hub.py 实现、docker-compose（增至 5 服务）与附录 A 第 4/5 条重启恢复语义；企业版多实例按“Redis 值流 + PG LISTEN/NOTIFY 控制事件”组合演进，接口预留不变。**

## D5 工程存储形态

**背景**：工程含 settings、页面组件树、变量、数据源、报警规则。读取模式：编辑器整存整取；运行期后端要按工程加载数据源/变量配置采集任务、加载规则。

**选项**：
- A 单 jsonb：`projects.doc` 一列整存。
- B 全拆表：pages、variables、datasources、alarm_rules 各自成表（组件递归成组树不适合全关系化，仍须 jsonb 存于 page 行内）。
- C 部分拆表：仅 variables / datasources / alarm_rules 出表，页面整体一个 jsonb。

**利弊对照**：

| 选项 | 优势 | 代价与风险 |
|---|---|---|
| A | 导出=取 doc、导入=存 doc，零转换；保存一个事务一列；schemaVersion 迁移一个函数（唯一实现点：前端 `migrateDoc()`，服务端只校验版本、失败 422 version_unsupported）；1MB 级 doc 整读在 P0 项目规模下成本可忽略 | 无外键级引用完整性——由保存/导入时校验（附录 A 第 2 条）补齐；无细粒度历史（企业版加版本表） |
| B | FK 天然完整性；变量/规则可独立查询 | 导出导入跨表组装；保存事务跨 5+ 表；schemaVersion 迁移分散；双端校验模型需做“行↔doc”双向映射；工作量约 A 的 2~3 倍，与“工程 JSON 导出导入是一等公民”的产品定位冲突 |
| C | 运行期加载配置不读整 doc | 出现“doc 与表”两份真相，编辑器保存要同步两处，导入导出仍要组装；而单工程 doc ≤1MB、项目数个位数到几十，该优化无论证必要 |

**对架构的影响**：决定 project_service 复杂度、导入导出流水线形态。
**耦合关系**：若 D5=B/C，D9B 的分享快照需改为按表组装冻结；导入导出（`GET /api/v1/projects/{id}/export`、`POST /api/v1/projects/import`）语义重写。D10 各选项在 B/C 下实现位置不同。
**落地：正文已按建议值 A（`projects.doc` 单 jsonb 整存）落地；若改选 B/C（拆表），需改动 dataModel（表结构，并需重新对照 G10 权威表结构裁决）、apiList（导出/导入接口语义）、realtime（运行期配置加载路径）。**

## D6 分享链接权限模型

**背景**：大屏要发给厂领导/客户看，还要 iframe 嵌入门户。分享页读者通常无账号；部署对象是内网单团队，无注册接口。

**选项**：
- A 匿名只读 token：nanoid 默认 21 字符（64 字符集，约 126 bit 熵），token 即凭证，可设 `expiresAt`、可停用。
- B 强制登录：分享页走 JWT。
- C token + 访问密码：先输密码换会话。

**利弊对照**：

| 选项 | 优势 | 代价与风险 |
|---|---|---|
| A | iframe 零交互嵌入；演示成本最低；支持到期与停用回收 | 链接泄露即可只读查看（内网部署 + 到期策略缓解）；**必须配套反滥用限流**（见下），否则泄露 token 可用脚本建大量连接拖垮单实例（评审确认的公开面防护缺口） |
| B | 可审计到人 | 大屏一体机与 iframe 无法便利登录；单团队定位下为观众再开账号体系，等于把 P2 角色权限提前做一半 |
| C | 比 A 多一道密码门槛 | iframe 场景必须先在某处输密码种 cookie，跨域嵌入 SameSite 问题多；演示体验差 |

**A 的强制配套（已按裁决参数落地）**：share token 并发 WS ≤20（`SHARE_MAX_WS_PER_TOKEN`）；同用户同工程 JWT WS ≤10（`JWT_WS_MAX_PER_USER_PROJECT`，编辑器/运行页连接共用该口径）；建连 ≤30 次/分（`RATE_LIMIT_CONNECT_PER_MIN`）。超限按 WS 错误协议处理：accept 后推 `error` 帧（`code=RATE_LIMITED`）再以统一 close code 4000 关闭，不做握手阶段 HTTP 429 分支拒绝（见 G17）。`/s/` 路径 `frame-ancestors` 默认放开（内网定位），如需收紧到指定父域在 Nginx 配置中改。
**对架构的影响**：决定公开分享端点（`GET /api/v1/share/{token}`）与运行态 WS（`/api/v1/ws/runtime`）的鉴权方式；限流器进入 ws_manager。
**耦合关系**：D6=A 依赖 D9 的分享快照语义（token 指向 `doc_snapshot`）与 D10 的出口脱敏；D6=B 与“匿名一键创建分享链接”的产品语义冲突。
**落地：正文已按建议值 A + 反滥用限流落地（限流参数取裁决值：token 并发 WS 20 / 用户×工程 WS 10 / 建连 ≤30 次/分）；若改选 B（强制登录），需改动 apiList 分享端点鉴权、realtime ws_manager 限流器与使用文档，并接受 iframe/大屏一体机登录不便；若改选 C，另需前端密码会话流程与跨域 cookie 方案。**

## D7 撤销重做实现

**背景**：画布操作频率高（拖拽每帧改状态）、动作种类多（移动/缩放/旋转/属性/图层/成组/页面），要求不产生拖拽中间态的垃圾快照。

**选项**：
- A 页面级全量快照栈：动作提交点（pointerup、属性面板防抖后）对当前页 components 树深拷贝（自写 util，不使用 structuredClone）入栈，上限 50 步，undo/redo 交换指针。
- B 命令模式：每类操作封装 do()/undo() 与反向增量。
- C Pinia 社区 undo 插件（如 pinia-plugin-undo-redo）：通用机制是对 store 的 action/状态变更做快照回放。

**利弊对照**：

| 选项 | 优势 | 代价与风险 |
|---|---|---|
| A | 实现集中一个文件（history.ts）；快照即状态，正确性直觉；按“提交动作”入栈天然过滤拖拽中间帧；内存可控（单页 ≤200 组件 × 约 1KB × 50 步 ≈ 10MB 上限） | 跨页操作（页面增删）需单独按页面快照处理；大 doc 克隆有毫秒级成本（可接受）；深拷贝统一走自写 util（不使用 structuredClone） |
| B | 内存最省；为未来协同扩展铺路 | 20+ 种命令类型各写正反逻辑；拖拽命令需维护坐标增量与吸附/成组状态一致性；成组与图层顺序的逆操作易出细节 bug；实现量约 A 的 3~5 倍，且 undo 正确性本就是高频缺陷区（骨架 R4），B 放大风险面 |
| C | 表面上少写代码 | 如实评估：插件以 store action 为快照粒度，画布高频变更仍需业务层手动划定动作边界，最终等于自建“提交点”机制；对深层嵌套组件树的快照/回放行为以插件实现为准（黑盒），不可控；换来的是一半 B 的约束加黑盒风险 |

**对架构的影响**：决定 editor store 的提交协议（所有修改入口须走 commit 快照点）。
**耦合关系**：与 D1 深度耦合（提交点=拖拽松手/吸附完成）；深拷贝统一走自写 util（不使用 structuredClone）；若 D11 改选 B/C，util 兼容面扩大。
**落地：正文已按建议值 A 落地（深拷贝统一自写 util，不使用 structuredClone）；若改选 B/C，需改动 editor store 提交协议与 history.ts；企业版若做协同编辑再评估命令模式。**

## D8 换算位置与告警阈值口径（评审必改项）

**背景**：评审确认各方案均未定义“用户配置阈值时参照显示值还是原始值”。骨架现状换算在绑定层、前端求值，后端告警引擎只能拿原始值评估——界面显示工程单位（72.5℃），阈值却要按原始量纲（725）配置。工业监控以工程值为口径是硬要求，必须统一。

**选项**：
- A 维持绑定级：数值换算字段挂在 `Binding`、前端求值（已废弃，统一口径见 B）。
- B 变量级、服务端求值：scale/offset/precision 上移 `VariableDef`，服务端采集入池（hub）前一次性换算为工程值；hub 中的值即工程值；告警阈值、WS 下发值、前端趋势缓冲、翻牌显示同口径。`Binding` 不含任何数值换算字段，仅保留 mode/mapping 表现层映射。
- C 双层：变量级换算 + 绑定级二次变换（如再百分比化）。

**结构示意（B，已落地）**：

```ts
export interface VariableDef {
  // ...骨架原字段不变（含 bitIndex 位提取：位号变量先位提取再换算）...
  scale?: number;      // 工程值 = 原始值 * scale + offset，服务端采集入池前一次性换算
  offset?: number;
  precision?: number;  // 服务端取位（四舍五入），告警阈值与下发同口径；仅 number 类型变量合法
}

export interface Binding {
  id: ID;
  prop: string;        // "fill" | "visible" | "props.text" 等目标属性路径
  variableId: ID;
  mode: 'value' | 'color' | 'visibility';
  // 表现层映射，与数据文档 §2.8 完全一致；Binding 上无数值换算字段
  mapping?: { kind: 'enum'; map: Record<string, string | boolean> }
          | { kind: 'range'; bands: { min: number; max: number; value: string | boolean }[] };
}
```

说明：`mapping` 为可选的枚举映射（值 → 颜色/文本/显隐目标值）或区间分段映射（min/max 区间 → 目标值）；数值换算（scale/offset/precision）只存在于 `VariableDef`，服务端入池前一次完成。

**利弊对照**：

| 选项 | 优势 | 代价与风险 |
|---|---|---|
| A | 换算语义紧贴“某组件想怎么显示” | 告警口径分裂（评审定性不可接受）；同一变量多处绑定时换算配置重复；调试面板/分享页/运行页多处前端实现必须一致 |
| B | 一处换算、全链路一个口径（“所配即所见”）；规则引擎、值帧、趋势缓冲天然一致；前端 binder 缩为纯映射；换算异常在服务端日志可见 | 变量定义多三个字段（校验：仅 number 类型允许配置）；“同一变量在不同组件显示不同单位”不支持（P0 外需求） |
| C | 极端灵活 | 两层换算叠加后用户难以推算最终值，配置错误面与文档解释成本最大，P0 无真实需求 |

**对架构的影响**：变更 `VariableDef`/`Binding` 结构、采集器→hub 链路（求值位置）、`binder.ts` 职责；schemaVersion 从 1 起步，无历史迁移负担。
**耦合关系**：D8=B 是 D3=A 的口径前提；若 D8=A，D3A 必须在使用文档显式声明“阈值按原始值配置”并接受评审指出的用户困惑。
**落地：正文已按建议值 B 落地（字段名统一为 scale/offset/precision，见第 0 节差异 1）；若改选 A/C，需改动 dataModel（`VariableDef`/`Binding`）、realtime（采集链路求值位置）、directory（`binder.ts`），并接受告警口径分裂问题。**

## D9 分享/发布语义：编辑直透 vs 分享快照

**背景**：骨架“分享页读实时 doc”存在契约缺口——编辑半成品直接上墙，且无停用/回收手段。产品要求“一键发布成大屏”，发布应是显式动作。

**选项**：
- A 实时直透（骨架现状）：`GET /api/v1/share/{token}` 返回当前 `projects.doc`。
- B 分享快照（已落地）：`share_links` 表含 `doc_snapshot JSONB`；创建/refresh 时冻结**脱敏后** doc；无 publish 状态机、无 `published_doc` 列；“发布”语义 = 创建或刷新分享链接；分享链路只读快照。
- C draft/published 完整状态机 + 版本历史（企业版候选）。

**接口示意（B，已落地）**：

| 接口 | 语义 |
|---|---|
| GET /api/v1/share/{token} | 公开、无鉴权读快照，返回 `doc_snapshot`（冻结时已脱敏）；token 无效/停用/过期返回 404 |
| GET /api/v1/projects/{id}/shares | 管理端：该工程分享链接列表 |
| POST /api/v1/projects/{id}/shares | 创建分享链接 = “发布”：冻结当前脱敏 doc 至 `doc_snapshot` |
| POST /api/v1/shares/{token}/refresh | 刷新快照 = “重新发布”：重新冻结当前 doc；对该 token 活动运行态 WS 推独立 reload 帧（客户端重拉 doc），不用 error 帧 |
| DELETE /api/v1/shares/{token} | 停用（置 `revoked_at`）；对该 token 活动 WS 推 error 帧（code=SHARE_REVOKED）后以统一 close code 4000 关闭 |

> 公开端单数 `/share/{token}` 与管理端复数 `/shares/...` 并存为**有意设计**（公开面与管理面分离），需在接口文档声明。

**运行口径披露**：采集与告警引擎始终按**最新保存的 doc** 热更新运行，分享快照只冻结画面呈现；变量删除/改名/换绑保存后，引擎按最新 doc 运行，已分享快照中旧变量无值流，对应组件显示空/停滞，刷新快照（重新发布）即恢复——属预期行为，需写入用户文档（“改了阈值需重新发布才体现在已分享大屏的画面与绑定上”）。若希望引擎也按快照版评估，将引入双引擎上下文切换，P0 不建议。
**多页语义**：share token 可带 `pageId` 仅作运行页定位，响应始终返回整份快照（不裁剪 doc），契约闭合，避免“部分发布”歧义。

**利弊对照**：

| 选项 | 优势 | 代价与风险 |
|---|---|---|
| A | 实现最少（零新增接口） | 编辑即上墙、无回退、无“发布”语义；误保存直接影响现场大屏（评审最高优先级移植的生产正确性缺口） |
| B | 快照创建/刷新/停用可控；半成品隔离；存储代价为每条分享链接一份快照（可忽略） | 需 `share_links` 表与 share 系列端点；需配套级联清理（附录 A 第 4 条） |
| C | 版本历史、任意回滚 | 版本表、diff、存储管理一整套，属企业版功能前置 |

**对架构的影响**：`share_links` 表结构、shares 服务、公开端点读路径、运行态连接的失效通知机制。
**耦合关系**：D9=B 依赖 D5=A（快照即整 doc 冻结，实现最简）；D9=A 则附录 A 第 4 条按直透语义改写（无快照可冻结），且须接受生产正确性缺口。
**落地：正文已按建议值 B（分享快照）落地；若改选 A（直透），需改动 dataModel（share_links 表）、apiList（share 系列接口）、realtime（快照读路径与 reload 帧）；若改选 C，属企业版功能前置。**

## D10 数据源凭证的存储与脱敏

**背景**：datasource config 含 EMQX/REST 的 username/password。doc 是导出导入与公开分享的数据体——出口不脱敏，等于“拿到分享链接/导出文件即拿到 broker 凭证”（评审必改项）。

**选项**：
- A 明文存 doc + 出口强制脱敏：库内明文（与多数自建工具一致）；所有出口（导出 JSON、分享快照 `doc_snapshot`、`GET /api/v1/share/{token}`、公开 WS 的 snapshot 中 datasource 元数据）按统一规则脱敏：`mqtt.config.password` 置空、rest/websocket headers 中敏感键（authorization/password/token/secret/key）置空、username 不脱敏；编辑器以 `passwordSet: true` 标记回显；PUT/导入合并规则：字段缺省或空串 = 保留库内值，显式 null = 清除。
- B 加密存库（已落地）：使用 cryptography 库 Fernet 加密（密钥 `.env: DATASOURCE_SECRET`），出口脱敏与合并规则与 A 完全一致。
- C 凭证外置：凭证不入 doc，独立表 `datasource_secrets` 按 datasourceId 关联；导出文件天然无凭证，导入后须重填。

**利弊对照**：

| 选项 | 优势 | 代价与风险 |
|---|---|---|
| A | 实现最小；符合内网单团队威胁模型（能碰库的人本就能改 .env）；开源同类产品（如 Grafana 数据源）同为库内保存、API 脱敏 | DB 拖库即凭证泄露；导出 JSON 不含密码，跨系统导入后需重填一次（一次性成本）；脱敏必须无条件执行，需契约 round-trip 测试覆盖（导出后密码必为空） |
| B | 拖库不直接泄凭证；出口脱敏语义与 A 相同，实现增量集中（一处加解密） | 新增依赖与密钥管理（密钥丢失=全部数据源不可用）；导入文件中凭证一律视为空（需重填） |
| C | 导出文件天然干净、语义最清晰 | 破坏“单文档整存整取”（与 D5A 冲突）；独立密钥表与导入关联是纯增实现面 |

**对架构的影响**：工程读取/保存（GET/PUT `/api/v1/projects/{id}`）出入参语义（`passwordSet` 标记、显式 null 清除）、share 快照冻结与导出函数的统一脱敏出口、pytest round-trip 用例（必须覆盖“清除凭证后导出导入”）。
**耦合关系**：D9B 的 `doc_snapshot` 冻结时必须同步脱敏；D2=B 会使凭证暴露面扩大到每个浏览器，与 A/B 任一选项冲突加剧。
**运行口径披露**：分享快照与导出 JSON 均为冻结物；工程保存（变量删除/改名/换绑）后，已分享快照中旧变量无值流，对应组件显示空/停滞，刷新快照（重新发布）即恢复；属预期行为，需写入用户文档。
**落地：正文已按建议值 B（库内 Fernet 加密，密钥 .env: DATASOURCE_SECRET）+ 出口统一脱敏落地；若改选 A（明文存库），需改动 dataModel 凭证存取与 .env 密钥项；若改选 C（凭证外置），另需改动 dataModel 表结构与导入导出实现。**

## D12 屏幕自适应方案

**背景**：同一大屏需适配不同分辨率的监控端（大屏一体机、普通显示器）。骨架方案为整体等比 scale：画布按基准设计尺寸布局，运行时在外层容器做 transform: scale 整体等比缩放适配（五种屏幕自适应模式的基准定义见架构文档“自适应方案”一节）。

**选项**：
- A 整体等比 scale 容器变换（骨架方案）：组件逻辑坐标恒为基准尺寸，运行态仅在外层容器做 scale。
- B 逐组件坐标比例换算：按容器实际尺寸比例重算每个组件 x/y/w/h 与字号。
- C 宽高分离适配：x/w 与 y/h 分别按不同比例换算，允许非等比拉伸填满。

**利弊对照**：

| 选项 | 优势 | 代价与风险 |
|---|---|---|
| A | 实现集中一处容器变换；编辑器所见即运行态所得；组件内字号/线宽随画布整体缩放，设备图元不变形 | 长宽比差异大时等比缩放留黑边 |
| B | 无黑边 | 每组件逐项换算，字号/线宽需单独适配；编辑器预览与运行态易不一致；文本不随画布缩放 |
| C | 满屏不裁切 | 非等比拉伸导致圆形表盘/状态灯/图标变形，设备图元视觉失真 |

**对架构的影响**：决定运行态渲染容器结构与编辑器画布坐标系（逻辑坐标恒为基准尺寸）。
**耦合关系**：与 D1 自研坐标模型同构（缩放只发生在容器层，组件坐标不需换算）。

## 附录 A：评审确认、不设选项、直接执行的强制修正项

1. 存活检查：新增 `GET /api/v1/health`（200 `{"status":"ok"}`），docker-compose 对 server 配置 healthcheck。
2. 引用完整性：保存/导入时校验 `bindings[].variableId`、`variables[].datasourceId`、`alarmRules[].variableId` 存在性，失败 422 并返回具体字段路径（统一错误体 `{code, message, errors:[{path, message}]}`）。
3. 编辑态级联：删除变量/数据源时弹出引用清单（绑定数、报警规则数），经确认后**一并删除关联绑定与报警规则**（删除，不是禁用，与 G12 一致；服务端 PUT 校验兜底 422）。
4. 运行态资源级联热清理：删除工程、停用 share token（`DELETE /api/v1/shares/{token}`）时——推送 error 帧并主动关闭相关活动 WS 连接、停止对应采集任务、清空内存变量池、将未恢复 `alarm_records` 标记 recovered（`recovered_at=now`）。导入总是新建工程（`POST /api/v1/projects/import`），不存在导入覆盖场景。
5. 报警防风暴：同一规则前端声音提示 60s 节流；单工程活动报警广播上限 200 条（超出按 critical > warn > info 优先保留并带 truncated 标记）；server 启动时将遗留 active 记录收口为 recovered。
6. 报警记录保留策略（按裁决默认值落地）：每日任务删除 `recovered_at` 早于 `ALARM_RETENTION_DAYS`（默认 30 天）的记录；单工程超 `ALARM_MAX_ROWS_PER_PROJECT`（默认 200000 条）滚动删除；参数进 `.env.example`。
7. MQTT 契约统一：默认 QoS 0 + clean session（防离线消息回放风暴）；QoS 1 为数据源可选项，文档声明回放风险。
8. 时间戳契约：数据源级可选 `tsPath`（载荷时间戳点路径，写入 `DataSource.config`），缺省以服务器接收时间为准；stale 判定与趋势 x 轴按该口径；载荷时间戳与服务器时间偏差 > ±5min（双向，含未来时间）视为不可信，回退服务器时间并记 warn。
9. 数据载荷边界声明：仅支持 JSON 载荷（`address + jsonPath` 提取）；CSV/十六进制/二进制上报明确不支持，写入 README 与组件协议文档，管理现场预期。
10. WS 访问日志脱敏：Nginx 对 `/api/v1/ws/runtime` 的日志关闭 query 记录或脱敏 token 参数，写入部署规范（统一交付基线）。
11. 变量测试注入面板：编辑器提供手动注入变量值入口（纯前端本地：编辑态预览会话内覆盖 runtime store，不落库不经服务端；运行态无注入），降低 M3/M4 联调成本。
